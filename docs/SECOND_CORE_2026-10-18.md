# Переход на второе ядро: расчёт и карта (2026-10-18)

Исходные цифры — из нагрузочного теста (`docs/PERFORMANCE_2026-10-17.md`, раздел
«Нагрузка») и замера прода 18.10.2026 06:27. Всё, что помечено «оценка», не
замерено и должно проверяться после шага 1.

> **Статус: ОТЛОЖЕНО (решение 2026-10-18).** Нагрузка 0,01 rps, продажи
> остановлены, проект ушёл в open source, где один процесс проще в развёртывании.
> Ошибка в ролях процессов грозит двойными сообщениями клиентам и двойной
> выгрузкой фида, а выигрыша сейчас нет. Это не микросервисы: тот же код и та
> же БД, только роль процесса. Пересмотреть при одном из условий: >6–8
> активных магазинов, рост p95 кабинета во время демпинга, деплои ощутимо
> рвут демпинг. Документ — готовый план на этот случай.

## Что есть сейчас

- На VPS **уже 2 ядра** (Xeon Gold 6226R, без HT). Второе ядро не «докупать».
  Его просто не использует наш главный процесс: `uvicorn --workers 1`.
- На втором ядре уже живут Postgres, nginx, Chromium/patchright (рывками, в
  момент замера ~50 % ядра), grafana и prometheus, lead/offer/lifesite-сервисы.
  Машина в целом: ~47 % CPU занято, ~53 % свободно, то есть свободно примерно
  одно ядро.
- RAM 3,9 ГБ, доступно ~1,6 ГБ, swap занят на 431 МБ. RSS kaspi-saas — 770 МБ.
- Postgres `max_connections=100`, сейчас занято 26. Пулы одного процесса:
  async 10+20 и sync 10+14, итого **до 54 соединений**.
- Реальная нагрузка ~0,01 запроса/с. Продажи остановлены с 10.10, проект ушёл
  в open source.

## Единицы расчёта

| Что | Цена в CPU |
| :--- | ---: |
| 1 запрос/с API | ~2,8 % ядра (92 % / ~33 rps) |
| 1 открытая вкладка кабинета (0,36 rps) | ~1 % ядра |
| Фон одного магазина (демпинг, радар, синки, чат-бот), Бархан 259 SKU | 4,3 % ядра в среднем |
| Postgres на магазин | ~1–1,5 % ядра (оценка) |

Рабочий потолок процесса — **70 % ядра**. Выше этого растут лаг event loop и
p95, а в одном loop с вебом живёт и демпинг.

Типичный магазин в пике = фон 4,3 % + 2 вкладки (владелец + менеджер) 2 % ≈
**6,3 % ядра** в главном процессе и ещё ~1,5 % в Postgres.

## Ёмкость: сейчас и после

| Конфигурация | Что упирается первым | Магазинов | Вкладок | rps на тесте |
| :--- | :--- | ---: | ---: | ---: |
| **Сейчас:** 1 процесс, всё вместе | одно ядро: веб + фон в одном loop | **~10–11** (70 / 6,3) | ~90 потолок, 40–50 комфортно | 30–34 |
| **Шаг 1:** веб (1 воркер) + фон отдельным процессом | процесс фона: 70 / 4,3 | **~16** | ~90 потолок, ~60 комфортно (вкладки получают целое ядро) | 30–34 (оценка: p95 стабильнее) |
| **Шаг 2:** 2 веб-воркера + фон | суммарно 2 ядра на всё, включая Postgres и Chromium | **~16–17** | ~150 потолок | **45–55** (оценка), не 68 |

Почему не ×2:

1. Второе ядро не пустое. Postgres работает на каждом запросе, и Chromium
   прыгает до половины ядра.
2. После разделения процессов первым упирается **фон**. Это один процесс на
   одно ядро, а 4,3 % на магазин растут линейно. 16 магазинов — это ~70 % ядра
   только на фон.
3. Нагрузочный генератор сидит на той же машине (10–15 % CPU), поэтому на
   повторном тесте цифра rps будет занижена.

**Итог: выигрыш ×1,5 по магазинам (10 → 16) и ×1,5 по rps. Шаг 1 даёт почти
весь выигрыш по магазинам. Шаг 2 нужен, только когда открыто больше ~60
вкладок одновременно.** При сегодняшних 0,01 rps ни один шаг ничего
измеримого не даст. Главная польза сейчас не в CPU, а в изоляции:

- деплой веба не рвёт цикл демпинга;
- падение фона не кладёт кабинет;
- тяжёлый синк не поднимает p95 интерфейса.

Дальше 16–17 магазинов поможет только третье ядро или вторая машина. Иначе
нужно дешевле считать фон: 4,3 % на магазин — это в основном радар и демпинг.

## Память и соединения

- **RAM (оценка):** веб без фона ~300–400 МБ, фон ~600 МБ плюс Chromium.
  - Шаг 1: +~300–450 МБ к сегодняшним 770 МБ. Влезает в доступные 1,6 ГБ.
  - Шаг 2: ещё +300–400 МБ. Это ~0,8 ГБ запаса при уже занятом swap. Перед
    шагом 2 замерить RSS веба после шага 1.
- **Postgres:** с текущими пулами 3 процесса × 54 = 162 > 100. Пулы нужно
  задать из env по роли:
  - веб: async 10+10, sync 5+5;
  - фон: async 5+10, sync 10+14 (там `to_thread`, 24 потока).
  - Итого ≤ 100 вместе с lead/offer-сервисами. Без этого под пиком будет
    `too many clients`.

## Карта: что в коде держится на «один процесс»

### A. Обязаны жить ровно в одном экземпляре (только в процессе фона)

Все 16 задач из `backend/main.py` `startup_event`, строки 123–149. Если
задача запустится дважды, это не замедление, а инцидент:

| Задача | Что будет при двух копиях |
| :--- | :--- |
| `offer_sync_loop` | два писателя цен, перерасход квоты 250 офферов / 30 мин |
| `feed_worker_loop` | двойная выгрузка фида (класс инцидента XML с 798 офферами) |
| `kaspi_chatbot_loop`, `outbound_loop`, `pickup_campaign_loop` | клиенты получают по два сообщения |
| `start_telegram_bot_polling` | Telegram 409 Conflict, бот глохнет |
| `start_billing_loop` | двойные начисления (проверить) |
| `background_dumping_loop`, sync-циклы, quality, health, ops digest | двойная нагрузка на Kaspi, ближе к бану WAF |

Решение: переменная `APP_ROLE=all|web|worker`. По умолчанию `all`, то есть
как сейчас, поэтому откат делается одной переменной. Задачи стартуют только
при `all`/`worker`. Страховка от ошибки в конфиге — `pg_try_advisory_lock` на
старте фона: второй экземпляр не берёт лок и не запускает циклы.

### B. Фон пишет, веб читает (ломается уже на шаге 1)

| Где | Проблема | Решение |
| :--- | :--- | :--- |
| `dumper/telemetry.py` + `routers/ws.py`, 6 мест `emit_telemetry*` | события фона не дойдут до WS браузера: сокет в другом процессе | Postgres `LISTEN/NOTIFY` (Redis на сервере нет). Веб слушает канал и раздаёт в WS. Payload ≤ 8 КБ |
| `routers/dumping.py:29` `_scheduler_states` | статус «следующий запуск / идёт сейчас» живёт в памяти шедулера, веб будет показывать заглушку | писать в БД (state-таблица магазина) |
| `routers/dumping.py:220` `POST /run` | ручной запуск демпинга пойдёт в веб-процессе, параллельно с циклом фона | проверить: либо ставить флаг в БД, который фон подхватит, либо лок на магазин в БД |
| `services/sales_orders_cache.py` + `state_helpers.py:1483` `bump()` | фон обновил продажи, а кэш веба об этом не знает | поколение в БД или короткий TTL |
| `state_helpers.py:35` `_mc_refresh_locks` | перелогин в кабинет MC могут запустить оба процесса сразу, это лишний подозрительный вход | `pg_advisory_lock(store)` вместо `threading.Lock` |
| `services/ops_metrics.py` `_counters` | дайджест в фоне не увидит счётчики, которые набрал веб | счётчики в БД или дайджест по каждому процессу |
| `feature_flags.py`, `billing/enforcement.py` | TTL 30 с, переключатель доедет с задержкой до 30 с | ничего не делать |

### C. Многошаговые сценарии в памяти веба (ломаются только на шаге 2)

Следующий запрос того же пользователя может попасть в другой воркер. Тогда
будет «job not found» или повтор:

- `routers/stores_auto_connect.py:54` `_pending`, `_jobs`, `_tasks` —
  автоподключение магазина;
- `routers/print_batcher.py:31` `_JOBS`, `services/print_batcher_service.py`
  `_STORE_PRINT_LOCKS`;
- `routers/pricefeed_import.py:81` `_PENDING` (в комментарии прямо сказано про
  перенос в БД/Redis);
- `routers/auth_v1.py` — rate limit «забыл пароль» по IP/email, лимит
  удвоится;
- `kaspi_wrapper.py` `_view_cache`, `_packaging_tabs_cache`,
  `invalidate_order_views` (1070/1135/1169) — после действия с заказом второй
  воркер покажет старое до истечения своего TTL.

Дешёвое решение для C — **липкость в nginx** по пользователю:
`hash $cookie_<сессия> consistent` или `hash $http_authorization consistent`.
Все запросы одного пользователя идут в один воркер, и почти весь блок C
снимается без переписывания. Честный перенос в БД нужен только для сценариев,
которые должны пережить рестарт.

Безопасно дублировать (только память ×2): `assistant/rag/index.py` `_CACHE`,
`analytics.py` кэши с TTL, `_merchant_id_cache`.

## План по шагам

**Шаг 1 — фон отдельным процессом (~1,5–2 дня):**

1. `APP_ROLE` в `startup_event` и advisory lock фона.
2. Размеры пулов из env по роли.
3. Задачи из блока B: NOTIFY для телеметрии, `_scheduler_states` в БД,
   `POST /run`, `sales_orders_cache`, `_mc_refresh_locks`.
4. `deploy/kaspi-saas-worker.service`: тот же app, `APP_ROLE=worker`, порт
   5001 без nginx, только `/health`. Основной юнит получает `APP_ROLE=web`.
5. `deploy.sh`: рестарт обоих юнитов, health-check обоих, откат обоих через
   `.last_good_sha`.
6. Проверка на проде:
   - ровно один «стартовал цикл» в `[Scheduler]`;
   - ни одного двойного сообщения клиенту за сутки;
   - WS-события доходят до кабинета;
   - повтор `perf_load.py`, RSS обоих процессов.

Откат: `APP_ROLE=all`, остановить worker-юнит.

**Шаг 2 — 2 веб-воркера (~0,5–1 день, когда понадобится):**

1. Два веб-юнита на :5000 и :5002 и nginx upstream с `hash … consistent`.
   Вариант `uvicorn --workers 2` не подходит: у воркеров один порт, и nginx не
   может закрепить пользователя за конкретным воркером.
2. Блок C: перенос того, что должно пережить рестарт.
3. Повтор нагрузочного теста. Цель — 45–55 rps.

**Когда делать.** Шаг 1 — когда активных магазинов станет больше ~6–8 или
понадобится, чтобы деплой не рвал демпинг. Шаг 2 — когда пиковых вкладок
станет больше ~60. При текущих 0,01 rps ни то ни другое по CPU не нужно.
