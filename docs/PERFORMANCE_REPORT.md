## 5. Железо: нужен ли апгрейд VPS

- Лаг event loop: 0.5151 (до) → 0.0029 (после), доля времени с блокировкой > 100мс.
- Загрузка CPU процессом: 0.0% (до) → 0.0% (после), доступно ядер: 1.
- Использование RAM системой (после): 76.1%, swap: 17.2%.

**Апгрейд CPU/RAM не требуется для устранения текущей проблемы.** Узким местом был не недостаток вычислительных ресурсов, а синхронные блокирующие вызовы на едином event loop (см. фиксы категории 0) — после их снятия лаг лупа упал на 99%, при этом CPU процесса не был насыщен ни до, ни после.

Отдельно: RAM системы занята на 76%, swap — на 17% (при 968 МБ RAM и 1 ядре на VPS) — это уже реально тесно для процесса, который держит открытым Chromium (Patchright) плюс Postgres на той же машине. Апгрейд CPU не даст эффекта, а вот **дополнительная RAM (до 2 ГБ) — разумная, недорогая подстраховка**, если планируется расти по числу сторов/фоновых воркеров.

## 6. Найдено, но не входит в категорию 0 (задачи на будущее)

- **`GET /api/orders` (14-28с) и `GET /api/transfers` (32-39с) — экстремально медленные сами по себе**, независимо от лага event loop (это `def`-роуты, идут через threadpool, не блокируют луп напрямую, но пользователь всё равно ждёт полминуты ответа). Причина — последовательный постраничный обход Kaspi REST API без параллелизации/кэша. Это `mc.shop.kaspi.kz`/`kaspi.kz`-кабинетная сторона → безопасный кандидат для Категории 1 (распараллелить пагинацию с ограниченной конкурентностью).
- **`kaspi.kz /shop/api/v2/orders` — 700 вызовов и ~170 МБ трафика за 49 минут** (крупнейшая статья трафика в системе) — это фоновые тики стокового радара (каждые 20с) и упаковки (каждые 30с), каждый из которых тянет полные `entries` заказа. Кандидат на сокращение полей ответа или локальный кэш между тиками — тоже Категория 1.
- **`kaspi.kz /shop/api/v2/pointofservices` — 224→281 вызов за 49 минут** — короткий кэш `discover_merchant_id()` в `states/session.json` либо не всегда попадает, либо это ожидаемо для legacy-запросов без `store_id`. Стоит перепроверить отдельно.
- **Внешний, не связанный с производительностью найденный риск:** на VPS `fail2ban` не установлен, sshd получает ~700+ неудачных попыток входа в час с внешних IP (это и роняло SSH-соединение деплоя в процессе этой сессии). Не трогалось в рамках этой задачи — стоит обсудить отдельно, установка/включение `fail2ban` низкорисковая и стандартная мера.
