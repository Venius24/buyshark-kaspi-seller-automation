## Cross-scene fix — pin-overlap race in `ScrollScrubVideo` (Hero cut short, title never showing)
User report: "Scene 1 doesn't play to the end and the title never appears" (this is the Hero race with the 2 competitor sharks + BuyShark, per `HIGGSFIELD.md`'s Scene 1 spec). Root cause was **not** in Hero's own logic — verified via instant `window.scrollTo` that Hero's progress→currentTime/title-opacity math was correct in isolation. The real bug: `ScrollScrubVideo` used to gate `ScrollTrigger.create()` (the pin + spacer) behind the video's own `loadedmetadata` event, an async wait. Meanwhile every synchronously-pinned scene (`SlotMachine`, etc.) measures its own `start:'top top'` at mount time, against whatever the page's layout looks like *then*. If Hero's `hero.mp4` (6.6MB) took longer to resolve metadata than the app-level `ScrollTrigger.refresh()` calls in `App.tsx` (fired on `document.fonts.ready`/`window.load`), SlotMachine's start position got permanently baked in against Hero's *pre-pin* (natural, unpinned) height — short by however many px the async gap covered. Confirmed via `getBoundingClientRect()`/computed `position` on all `<section>` elements at `scrollY≈3150`: **both** Hero and SlotMachine were simultaneously `position:fixed;top:0`, with SlotMachine (later in DOM) painting over Hero — hiding Hero's last ~30-40% of scrub (exactly where the title fades in per `(progress-0.72)/0.28`) before it ever got there.
- **Fix:** removed the metadata gate entirely. `ScrollScrubVideo`'s `ScrollTrigger.create()` now runs synchronously in the mount effect, same as every other scene — no more async race for anyone measuring against it. `video.duration` is read fresh inside `onUpdate` instead (guarded with `Number.isNaN`, since it's `NaN` until metadata resolves) rather than captured once at setup time; until it resolves, `onUpdate` just skips the `currentTime` write for that tick and the scroll-driven `onProgress` callback still fires normally.
- **Standing rule for this file:** never gate a `ScrollTrigger.create()` call (pin creation) on anything async (video metadata, image load, font, etc.) — it silently breaks every trigger measured after it in the DOM. If a value from that async resource is needed inside the trigger's callbacks, read it lazily inside the callback instead of blocking trigger creation on it.
- This affects all three `ScrollScrubVideo` users (Hero, Scene 4, Scene 6) — same fix covers all of them since it's in the shared component, not scene-specific code.

## Scene 2 — Round 4: drop the blade, fix the backlight's hard edge, add a 5th role
User sent a screenshot showing a visible rectangular edge clipping the backlight glow top/bottom, asked to drop the blade-sweep effect entirely, and asked for a new role: "Ручной правки остатков" (manual stock/inventory correction).

Verify actual recap playback timing in a real, focused, non-automated browser during the final QA pass before assuming it's fine.

- Two throwaway generations before the final one: take 1 used the pre-`HIGGSFIELD2.md` brief (massive rack, dozens of red emblem medallions) — scrapped for being both too large and using tiled emblems instead of one rim. Take 2 fixed size/rim per `HIGGSFIELD2.md` but had no sharks (CSS swarm was the plan at that point) — scrapped once the CSS approach itself was rejected. Take 3 (final) folds both fixes plus the baked-in shark swarm into one prompt. All raw takes kept in `HIGGSFIELD/scene4/` (gitignored scratch) in case any element needs revisiting.
- **Lesson worth generalizing:** when a scene's brief includes a repeating/periodic visual effect (pulses, swarms, flickers), default to asking whether the user wants it baked into the generated video vs. built as a DOM/CSS overlay *before* building the CSS version — this is the second time in this project a DOM-driven "cheap" approach was rejected in favor of "just put it in the Higgsfield footage" (first was implicitly Scene 2/3's reliance on real video for anything that needs to look expensive). CSS-driven periodic effects are fine for UI chrome (radar sonar sweep in the Preloader, reel blur in Scene 2) but weaker for "this should look like real cinematic wildlife/particle behavior."

## Scene 6 — CTA jaws (skips Scene 5 for now)
User explicitly deferred Scene 5 (sea-battle FAQ/comparison) to be redone later and asked to jump straight to Scene 6 per `HIGGSFIELD2.md`'s unchanged brief: jaws open on the viewer, camera flies inside, signup panel lives in the mouth.
- One Higgsfield `seedance_2_0` video (8s/720p/std, ~36 credits): extreme close-up on the biomechanical carbon-fiber shark head (same design language as the Hero shark asset — cyan circuit-line accents, not a generic organic shark), jaws opening directly at camera baring teeth, then a fast push through the throat into a dark alien-organic interior chamber lit by cyan/red bioluminescent pods — reads like a control room glimpsed inside the predator. One take, no rejects needed this round.
- Re-encoded with the same `-g 3 -keyint_min 3` high-keyframe pass as Hero/Scene 4 and wired through `ScrollScrubVideo` (`scrollMultiplier=2.2`) — scroll depth maps directly to how far the camera has plunged into the mouth, same mechanic as Hero's hyperdrive approach.
- Signup panel (`CtaJaws.module.css` `.panel`) fades/scales in over the last 30% of scrub progress via the same imperative ref/style pattern as Hero/Scene 4 (`onProgress` mutating DOM directly, no React state). Panel border uses a zigzag `clip-path` (alternating polygon points along the top and bottom edges) so its silhouette reads as a row of teeth framing the HUD — a pure-CSS callback to "you are inside the mouth" without needing a separate video/image asset for the frame.
- Button hover effects (spec: "вибрация, бас-дроп и рык акулы" — vibration, bass drop, shark roar): implemented as (1) a CSS shake keyframe re-triggered via `classList.remove` + forced reflow (`void btn.offsetWidth`) + `classList.add`, since re-adding the same class name doesn't restart a CSS animation on its own; (2) a full-bleed radial red `.flash` overlay snapped to opacity 0.9 then GSAP-eased back to 0 (a visual "bass drop" hit); (3) a **synthesized** Web Audio bass/growl sound — sawtooth oscillator sweeping 190Hz→36Hz plus a lowpass-filtered noise burst, both built entirely in-browser with no recorded SFX file. This matters because Higgsfield's audio tool (`generate_audio`) is TTS-only — there's no standalone sound-effect/music model available outside the game-generation pipeline, so a real "shark roar" sample wasn't an option here. The synth call is wrapped in try/catch since some browsers may still block it depending on prior interaction state; the visual shake+flash land regardless. If a future pass wants a more convincing roar, the fix is an external recorded/library SFX asset, not more Higgsfield spend on this tool.
- `ScrollScrubVideo`'s `<video>` is always `muted`, so any audio baked into the background video itself would never be heard — this is why the roar had to be a separate hover-triggered Web Audio effect rather than something baked into the cinematic video (unlike Scene 4's shark swarm, which *should* be baked into video since it's ambient/continuous, not a discrete interaction response).
- Task tracker: Scene 5 (#6) stays `pending` intentionally — not skipped-and-forgotten, the user wants it replaced with a different concept later. Don't build the placeholder FAQ content further until that direction is given.
- **Ambient loop for the frozen end-state:** `ScrollScrubVideo` freezes on `currentTime = duration` once scroll progress hits 1 — a static image, not ideal for a scene that's meant to hold the visitor's attention at the CTA. Per user request, extracted the true last frame of `scene6-bg.mp4` (`ffmpeg -sseof -0.1 -vframes 1`), uploaded it via `media_upload`/`media_confirm`, and used it as `start_image` for a second Higgsfield generation (8s/720p/std, ~36 credits) prompted for near-static, slow hypnotic pulsing of the same bioluminescent chamber — so the handoff from frozen-frame to live-loop is visually seamless (same composition, just continues breathing).
- **Loop construction, per explicit user correction:** first attempt used an `xfade` crossfade (splice the last 0.4s into the first 0.4s) to hide the seam — user rejected this approach and asked for **forward-then-reverse (boomerang)** instead: `ffmpeg ... [0:v]split[a][b];[b]reverse[r];[a][r]concat=n=2:v=1:a=0[v]`. This guarantees a mathematically exact seam (the loop's last frame *is* its first frame) rather than an approximated blend, at the cost of double the duration (16s) and roughly double the file size (~10.4MB) for a single ambient clip. **Prefer boomerang over crossfade for any future ambient/hypnotic loop in this project** — simpler, exact, and the extra file size is a non-issue for a background loop that only plays after the visitor has scrolled deep into a scene.
- Wiring: a second `<video>` (`loopRef`, autoplay/loop/muted, `.loopVideo` — `position:absolute; inset:0; z-index:0; transition: opacity 0.6s ease`) sits behind the vignette inside `ScrollScrubVideo`'s children, always playing in the background but at `opacity:0` until `onProgress` reports `progress >= 0.985` (`LOOP_IN_AT` constant in `CtaJaws.tsx`), then fades to `opacity:1` via the CSS transition (a plain style-flip here, not GSAP, since it's a rare boolean toggle rather than a per-frame continuous value — matches the project's convention of reserving GSAP/imperative tweening for continuous scroll-driven values). Scrolling back up past that threshold fades it back out and the frozen scrub-video frame takes over again, so it's fully reversible.

## Scene 3 — Round 4: chip centering fix + won-card polish + scroll-in "wow" entrance
- **Chip offset bug**: `.wonChip` had been positioned with `top: -22%` plus its own `transform: translateX(-50%)`, which floated it noticeably above the card slot (close enough to the title row to look wrong) rather than sitting where the card used to be. Root cause of *why it couldn't just be recentered in place*: the chip is also animated by GSAP (`gsap.set/to(chip, { y, scale, opacity })`), and GSAP's transform tweens overwrite an element's *entire* transform with their own decomposed values — so putting a percentage-based `translate(-50%, -50%)` directly on the GSAP-animated node would get silently destroyed the moment `y`/`scale` are first set. Fixed by splitting it into `.wonChip` (outer, pure-CSS `top:50%; left:50%; transform:translate(-50%,-50%)` centering, never touched by GSAP) wrapping `.wonChipInner` (the actual GSAP target, no competing transform of its own). Same category of gotcha as the earlier `translateX(%)`-resolves-against-own-box bug from Scene 2 — percentage-based transforms and GSAP transform tweens don't mix safely on the same element.
- **Won-card visual polish**: turned the `ВАШ МАГАЗИН` tag into an actual small glass card (green border + pulsing green glow `wonGlow`, matching the main `.crate` material) instead of bare floating text, per explicit request to make it "more beautiful." `--win-green`/`--win-green-dim` added to `tokens.css`.
- **Scroll-in entrance ("wow effects")**: added a one-time `ScrollTrigger` (`start: 'top 75%', once: true`) that materializes the 3 cards as if powering on — staggered per card (`0.18s` apart): scale/blur/opacity in from `{opacity:0, y:70, scale:0.5, blur:16px}` with a slight overshoot (`scale:1.06` then settle via `elastic.out`), plus a one-shot radial `.powerFlash` overlay per card that flares and fades right as it lands. Previously the cards had zero entrance treatment — they were just statically present whenever the section scrolled into view.
