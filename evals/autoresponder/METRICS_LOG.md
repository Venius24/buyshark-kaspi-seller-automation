# Журнал метрик ИИ-автоответчика

Сюда записывается **каждый** замер: и удачный, и неудачный, в порядке получения. Старые строки
не правятся и не удаляются. Исправление ошибки — новая строка со ссылкой на старую.

Обозначения:
- **κ** — каппа Коэна между судьёй и ручной разметкой владельца.
- **4 класса** — ok / inexact / unsupported / should_escalate по 167 ответам бота.
- **ok vs rest** — «ответ ok» против остального.
- **годился** — бинарный вопрос по всем 195 строкам: «черновик можно было отправлять» (ответ ok или inexact; эскалация «лишняя»).
- **dev / test** — половины диалогов (хеш group_id). На dev правится рубрика судьи, test отложен для отчёта.

## 3. Остановка 2026-10-20 — итог и почему стоим

**Почему остановились.** Баланс OpenAI-ключа (`OPENAI_API_KEY` из `.env`), на котором работал судья, исчерпан: прогон 2.3 получил `HTTP 429: You have no credits remaining` на всех 191 вызовах судьи. Весь баланс (~$9.2 плюс пересказ набора) ушёл на калибровку судья↔разметка (1.1–1.10), замер «до» (2.1) и прогоны 2.2–2.3. Это ошибка ведения работы: перед платными прогонами не названа общая оценка стоимости и не согласован лимит. Владелец был против такого расхода. Без судьи нельзя измерить качество отправленных ответов, поэтому замер «после» не сделан.

**Что измерено и чему можно верить:**
- База «до» по ручной разметке (раздел 0) не менялась.
- Судья `gpt-5.5`, рубрика v3: κ = **0.65** против ручной разметки в бинарном вопросе «ответ годится» (88.7 %, 195 строк). Его 4-классовому вердикту (κ ≈ 0.3) верить нельзя. Это калибровка через OpenAI API; другой судья (например, через Codex) — другая связка, её надо калибровать заново на тех же 195 строках.
- Регрессия «до» (2.1, код `b7b9ae12`, судья gpt-5.5, ×3): success **73.9 %** (65.7–81.7), handoff recall 81.8 %, лишние эскалации 11.3 %, unsupported 15.8 % от отправленных.
- 2.2 недействителен (JSON mode DeepSeek, пустые ответы). 2.3 — только детерминированные метрики: recall 82.8 %, лишние 12.8 %, 0 сбоев API, 297/297 ответов в JSON, p95 латентности 2677 мс.

**Что сделано в коде (не закоммичено, на прод не уходило):**
- `backend/chatbot/pipeline.py`: проверки до и после модели вынесены из воркера, воркер, eval и раннер воспроизведения вызывают одни функции.
- `backend/chatbot/llm.py`: конфиг `CHATBOT_LLM_*`, таймаут, ретраи на 429/5xx/сетевых ошибках с общим дедлайном, structured output через вызов функции `send_reply` (не JSON mode — см. 2.2), трасса вызова: латентность, попытки, токены, стоимость при заданных ценах, режим разбора, версия промпта.
- Журнал ответов: миграция 053 (`latency_ms`, `llm_attempts`, `cost_usd`, `prompt_version`, `llm_parse`), токены теперь пишутся и для эскалаций моделью. Метрики Prometheus: вызовы LLM по результату и режиму разбора, ретраи, стоимость.
- Правки по причинам ошибок (**ещё не измерены**): стем `передал` сужен до «передал ваш / вопрос / запрос…»; казахские формы жалоб («сынып кел/боп/бол…», «басқасын», «салмады», «жетіспейді»…; голое «сынып» не используется: это ещё и «класс»); блок промпта «ДОСТОВЕРНОСТЬ» (характеристики и наличие только из данных, ссылки и фото не подтверждать, просьба о реальном фото → менеджер, без «уточню/проверю», без описания меню Kaspi); исключение: адрес и дата доставки → Kaspi Гид без метки; в фактах самовывоза «ещё собирается» заменено на «отметка в Kaspi может отставать, при вопросе о готовности — менеджер». Правило 8 владельца (голосовые) не тронуто.
- Тесты автоответчика и метрик проходили (180) до последней правки промпта, после неё не перезапускались.

**Побочная находка.** `deepseek-chat` у DeepSeek теперь алиас `deepseek-flash` (поле `model` в ответе API, список моделей ключа: `deepseek-flash`, `deepseek-v4-pro`). Прод уже работает на другой модели, чем в базе «до» из раздела 0.

**Что дальше (план на 2026-10-21):**
1. Перезапустить тесты после правок промпта.
2. Судья через Codex (подписка, без API-кредитов). Это тоже LLM-as-a-judge, но новая связка: сначала калибровка на 195 строках (dev/test, та же рубрика v3), затем сверка с gpt-5.5-судьёй.
3. Перемерить «до» (код `b7b9ae12`) и «после» одним и тем же судьёй, сравнение `--compare`.
4. В раннер — `--max-cost` и оценка стоимости до запуска. Перед любым платным прогоном называть цену и получать лимит.
5. CI: детерминированная часть (маршруты, стемы, полнота эскалаций на наборе без модели) — в pytest на каждый пуш; прогон с судьёй — локально через Codex, результат коммитится в `results/`.
6. Документация (`docs/AUTORESPONDER_EVAL.md`: раздел «до/после»), HANDOFF, коммит, деплой (миграция 053).

## 5. Решения бота: answer / clarify / safe_unknown / escalate (2026-10-20, день)

**Что изменено (решения владельца после раздела 4):**
1. Самовывоз всегда готов к выдаче, его собирают на месте при приходе клиента. Ограничение одно — часы работы точки. Факт в `order_context` больше не зовёт менеджера на «готово?».
2. Модель возвращает `action`: `answer` (знаю и отвечаю), `clarify` (не понял и спрашиваю), `safe_unknown` (понял, но ответа не знает и магазин, например логистика Kaspi, — честно говорю, куда обратиться), `escalate` (нужен человек). Handoff — только `escalate`. Решение пишется в `chat_response_logs.llm_action` (миграция 053, ещё не накатана) и в Prometheus `chatbot_llm_actions_total`.
3. Новые метрики (`decision_metrics` в `run.py`, по прогонам):
   - **answer quality** — доля годных (ok/inexact по судье) среди отправленных ответов;
   - **escalation recall** — доля эскалаций там, где по разметке нужен человек;
   - **escalation precision** — среди эскалаций в кейсах с известным ответом доля тех, где человек нужен. Эскалации в спорных кейсах (inexact/unsupported) считаются отдельно;
   - **autonomy rate** — доля прогонов, закрытых ботом без менеджера;
   - **resolved by bot** — бот ответил сам, и судья счёл ответ годным: доля от всех прогонов.

   Для старых прогонов `action` выводится из исхода: эскалация → escalate, ответ → answer. Пересчёт: `run.py --summary FILE`, исходные файлы не меняются. Судья и рубрика v3 не менялись, калибровка (раздел 4) действует.
